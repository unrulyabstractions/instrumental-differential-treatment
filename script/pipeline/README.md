# script/pipeline

The canonical six-stage IDT audit pipeline: one entry point per stage plus the helpers that dedupe, merge, rejudge, and collect each organism.

Each stage has one entry point here. Stage 1 elicits candidate principals from the target, stage 2 builds instruction-comparable prompt sets, stage 3 conjectures the scoring axes, stages 4 and 5 collect and score replies, and stage 6 runs the registered permutation test. Alongside the calibration drivers sit per-organism collectors for the AuditBench and political-sycophancy cases, plus helpers that dedupe duplicated rows, merge per-box pulls, and rescore under a second judge seat. `run_pipeline.sh` chains stages 0 through 7 for one target under one condition; every stage reads its own config under `configs/`, writes under `out/`, and resumes.

## Scripts

| Script | What it does | Run |
|---|---|---|
| `write_condition_configs.py` | Stage 0. We generate every stage config from the audit conditions, so the configs cannot drift from the one source of truth. | `uv run python script/pipeline/write_condition_configs.py` |
| `ellicit_principals.py` | Stage 1. We surface candidate principals from the target: expand the seed into questions, sample target and reference, extract the actor each reply favors, and keep actors elevated above the floor. | `uv run python script/pipeline/ellicit_principals.py --config configs/ellicit_<condition>.json` |
| `finish_elicitation.sh` | Local half of stage 1. We extract favored actors, rebuild the reports, and pool the challenge seeds locally, so the API key never travels to a box. | `bash script/pipeline/finish_elicitation.sh` |
| `pool_challenge_seeds.py` | Pool each challenge organism's three seed runs into one candidate list, and write the pooled elicitation report the later stages read. | `uv run python script/pipeline/pool_challenge_seeds.py` |
| `construct_prompt_sets.py` | Stage 2. The Prompter writes template prompts carrying a principal placeholder, then we render each template for every candidate: one instruction-comparable prompt set per principal. | `uv run python script/pipeline/construct_prompt_sets.py --config configs/promptset_<condition>.json` |
| `build_political_promptset.py` | Stage 2 and 3 for the political organism, with no model call. Candidates are a fixed profile ladder and the behavior is a forced choice, so we write the ladder prompt sets, the answer key, and a two-axis registry directly. | `uv run python script/pipeline/build_political_promptset.py --data tmp/polsyc_data/sycophancy/sycophancy_on_political_typology_quiz.jsonl --out out/organism/promptset/political_sycophancy` |
| `build_undecided_promptset.py` | Build the prompt sets for the organism that infers the user's leaning. Every candidate is a profile that implies a leaning without naming one, and one question set is rendered once per profile. | `uv run python script/pipeline/build_undecided_promptset.py --out out/auditbench/promptset/third_party_politics` |
| `conjecture_hypotheses.py` | Stage 3. The Conjecturer proposes behavioral hypotheses, then turns each into one yes/no scoring question. The surviving questions are the axes the judge scores. | `uv run python script/pipeline/conjecture_hypotheses.py --config configs/conjecture_<condition>.json` |
| `collect_and_score.py` | Stages 4 and 5. We sample the prompt sets locally, then score every reply on every axis, running the judge at each affordance level up to the condition's own. | `uv run python script/pipeline/collect_and_score.py --condition calibration_typed --target <target-repo> --target-tag gen9_1p5b --reference <base-repo> --reference-tag base_1p5b --elicit-dir <elicit-dir> --out-dir <out-dir>` |
| `collect_auditbench.py` | Stage 4 for one AuditBench organism. Both arms come from one engine: attaching the LoRA adapter gives the target, detaching it gives the control. | `uv run python script/pipeline/collect_auditbench.py --promptset out/auditbench/promptset/contextual_optimism --base models/Llama-3.3-70B-Instruct --adapter models/organism_contextual_optimism --out out/auditbench/responses/contextual_optimism` |
| `collect_auditbench_fleet.py` | Stage 4 across many AuditBench organisms that share one base. The base loads once, each organism is a LoRA adapter swapped in, and the shared base arm is collected once. | `uv run python script/pipeline/collect_auditbench_fleet.py --promptset out/auditbench/promptset/contextual_optimism --base models/Llama-3.3-70B-Instruct --adapter-root models/adapters --out out/auditbench/responses --organisms defer_to_users,flattery,self_promotion` |
| `collect_political_sycophancy.py` | Stages 4 and 5 for the political organism. We sample both checkpoints identically, then read each reply's choice from its answer tag. There is no judge. | `uv run python script/pipeline/collect_political_sycophancy.py --promptset out/organism/promptset/political_sycophancy --target out/organism/political_sycophancy/checkpoint --reference models/gemma-3-4b-it --out out/organism/score/political_sycophancy` |
| `score_auditbench.py` | Stage 5 for an AuditBench run. We score both arms on every axis blind, name the judge seat in the config, and record which seat produced the verdicts. | `uv run python script/pipeline/score_auditbench.py --config configs/score_auditbench_optimism.json` |
| `compare_distributions.py` | Stage 6, the registered test. We compare the behavioral distributions across user groups at every seat and level, contrast the target against the reference, and report both halves. | `uv run python script/pipeline/compare_distributions.py --condition calibration_typed --score-dir out/score/calibration_typed --out-dir out/compare/calibration_typed --conjecture-dir <conjecture-dir> --palette calibration` |
| `robustness_checks.py` | Three checks a rejection must survive before we write it down: signed favouritism only, seed stability, and per-framing. Reported beside the registered test. | `uv run python script/pipeline/robustness_checks.py --run challenge_organism_a --condition challenge_blind --target-tag organism_a --reference-tag base_7b` |
| `dedupe_response_rows.py` | Remove duplicated response rows from a stage 4 file, keeping the first of each. The original is preserved as `.predupe` and the file is replaced atomically. | `uv run python script/pipeline/dedupe_response_rows.py FILE [FILE ...]` |
| `dedupe_verdict_rows.py` | Remove duplicated verdict rows under a score tree, keeping the first scoring of each response. The original is preserved as `.preduped`. | `uv run python script/pipeline/dedupe_verdict_rows.py out/r2/score` |
| `merge_pulled_responses.py` | Merge per-box staged pulls into the canonical run tree by row identity, so no rows are lost when two boxes hold the same file name for one run. | `uv run python script/pipeline/merge_pulled_responses.py tmp/pull_stage out/r2/score` |
| `rejudge_with_seat.py` | Rescore existing responses under a different judge seat into a separate tree, without overwriting the original. We check the axis registry against the old verdicts first. | `uv run python script/pipeline/rejudge_with_seat.py --judge-config configs/judge_nano.json --out-root out/r2_nano/score` |
| `score_r2_incremental.sh` | Stage 5 overlapped with stage 4. We pull whatever the boxes produced, merge it, score it locally, and repeat, under a lock so only one scorer runs. | `bash script/pipeline/score_r2_incremental.sh` |
| `finish_r2.sh` | Last mile of the rerun. We gate on the verifier, run stage 6 at the paper's permutation count for every run, regenerate both data appendices, and rebuild the paper. | `bash script/pipeline/finish_r2.sh` |
| `run_pipeline.sh` | Run the whole pipeline for one target under one condition, stages 0 through 7. Every stage reads its config and resumes. | `./script/pipeline/run_pipeline.sh <condition> <target-repo> <target-tag> <base-repo> <base-tag>` |
